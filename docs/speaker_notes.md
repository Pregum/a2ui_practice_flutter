## 04 そもそも A2UI とは？

**コラム: A2UI の立ち位置**
- Google が公開したオープンプロジェクト（Apache 2.0）。公式サイトは a2ui.org、リポジトリは github.com/google/A2UI。CopilotKit などコミュニティの貢献も入っている。
- 一言でいうと「**エージェントの返事を、安全に・どのプラットフォームでも・操作可能な UI として描画するための共通フォーマット**」。
- ポイントは「実行コードを送らない」こと。エージェントが送るのは宣言的な JSON（コンポーネントの木＋データモデル）だけで、クライアントは**自分が信頼するカタログ**のウィジェットにしかマップしない。だから UI インジェクションや任意スクリプト実行のリスクを構造的に避けられる。
- JSONL ベースでストリーミングに最適化されており、「エージェントが考えながら UI が組み上がっていく」progressive rendering が公式の売り。
- 同じペイロードを Angular / React / Flutter / SwiftUI など各クライアントが自前の部品で描ける＝**見た目の統制権はアプリ側**に残る。
- 本デモは v0.9 を Flutter で自前実装（パーサ→バリデータ→レンダラー）。プロトコルが軽量なので、フルスタックのSDKを待たずに自分で実装できるサイズ感、というのも伝えたいポイント。

## 15 実際に遭遇した罠：2回目の生成から壊れる

**コラム: 発表当日の朝に踏んだバグの裏話**
- 前日まで動いていたデモが当日朝に全滅。1回目の生成は必ず成功するのに、2回目から「o o o o…」「bolbolbol…」のような縮退ループに入る。
- topK=1（greedy）にしていたおかげで**毎回同じように壊れる**＝再現性があり、切り分けが早かった。「1回目に成功したプロンプトをもう一度流すと壊れる」ことから、プロンプトではなく実行順序の問題と特定。
- flutter_gemma 0.16.5（前日リリース）の changelog に「KV-cache bleed between sequential chats を修正」とあり当たりに見えたが、上げても完治せず。最終的に「生成のたびにエンジンごと作り直す」力技で回避。モデルファイルは OS のページキャッシュに乗っているので再作成は5〜10秒で済む。
- 教訓: ①小型モデルの暴走は「ガード（2000字打ち切り）＋生出力ログ」を仕込んでおくと調査が速い ②オンデバイス推論はランタイムがまだ若く、こういう罠は普通にある。発表デモは「確実に動く最小構成」に絞るのが正解。

## 20 実機デモ（Pixel 6a・オフライン）
