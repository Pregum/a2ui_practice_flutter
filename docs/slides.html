中心思想：LLM とレンダラーを疎結合に。重い側はインターフェースの裏へ。

06A2UIプロトコル：4種のメッセージ

JSONL（1行1メッセージ）。トップレベルキー1つで判別。

メッセージ役割
createSurface画面を作る（最初に1回）
updateComponentsコンポーネントを置く（root必須・フラット配列）
updateDataModel表示データを入れる（path = JSON Pointer）
deleteSurface画面を消す

全メッセージに "version":"v0.9" を含める。

07構造：隣接リスト × JSON Pointer

親子は id 参照（隣接リスト）

[{"id":"root","component":"Card","child":"col"},
 {"id":"col","component":"Column",
  "children":["a","b"]}]

フラット配列 → renderer が id で木を再構築

動的値は JSON Pointer

// propの中
"value":{"path":"/edit/style"}

// 別送される実データ
updateDataModel
  path="/edit" value={...}

"path"1キーのMap → dataModelから解決

09見せ場：progressive rendering

小型モデルは生成が遅い。
それを弱みではなく見せ場に変える。

token stream → [行バッファ] → 改行で確定 → parse → message
   createSurface        ──► 空の画面
   updateComponents(root) ─► 画面が"出る" ◄── ここで描画開始
   updateComponents(...) ──► 追加分を埋める
   updateDataModel      ──► 文言・値が"入る"

rootさえ来れば描画開始。遅い端末ほど progressive が活きる。

10バリデーション & 自己修正ループ

generate→ parse→ validate→ render ↩ fail repair prompt
失敗自己修正での指示
rootが無いid=rootを必ず1つ含める
未定義idを参照childrenのidは必ず定義する
カタログ外の型8種以外は禁止
コードフェンス混入JSON以外を出力しない

リトライ上限2回で打止め → エラーUI

15改めて：どこが LLM（動的）か

静的（事前実装・固定）

▸ カタログ＝コンポーネント定義
InquiryHeader / ReplyBox / …
▸ レンダラー（component → Widget）
▸ パーサ / Validator / データモデル
▸ システムプロンプト

＝ 部品と「組み立て工場」

動的（LLMが実行時に生成）

▸ どのコンポーネントを選ぶか
▸ どう並べ・入れ子にするか
＝ surface の構造
▸ 文言・データ
件名 / 会話 / 返信ドラフト

＝「献立と盛り付け」だけ。Dartもピクセルも書かない

// 同じ1行に静的と動的が同居している
{"component":"InquiryHeader",          ← 型はカタログ語彙（静的）
 "subject":"請求額が二重","priority":"high"}  ← 中身はLLM（動的）

LLM が書くのは JSONの設計図だけ。実装(部品)は全部アプリ側。
